# 🔴⚪ 경기 채팅방 실시간 그래픽 — 기술 선택 기록

> **작성일** 2026-08-11 · **범위** `src/components/Chat/stadium/`
> **배포** Vercel (프론트) / Spring Boot (백엔드, 직접 개발)

처음엔 "WebGPU 같은 신기술을 써보고 싶다"에서 출발했다. 그런데 우리 사용자가 어떤 상황에서 이 화면을 보는지 정리하고 나니 판단이 꽤 달라졌다. 이 문서는 그 과정을 남긴 것이다.

**미리 밝혀둘 것** — 아래 수치는 대부분 **산술 추정**이다. 실기기 프로파일링은 아직 못 했다. 계산이 맞는지는 10절에 남겨뒀다.

---

## 1. 우리 사용자는 어떤 상황인가

이걸 먼저 정리한 게 이번 작업에서 제일 도움이 됐다. 기술을 고르기 전에 **제약을 먼저 알아야 했다.**

경기 채팅방 사용자는 대체로 이렇다.

> **쿠팡플레이로 경기를 틀어놓고, 그걸 보면서 우리 채팅방에 들어와 채팅을 친다.**

여기서 나오는 조건들:

### ① 사용자는 우리 화면을 보고 있지 않다

시선은 경기 중계에 있다. 채팅방은 **곁눈질로 보다가 할 말 있을 때 들어오는 화면**이다.

→ 상시로 화려한 배경이 돌아가면 그건 그냥 배터리만 먹는다. **연출은 짧고 강하게, 나머지 시간엔 조용히.**

### ② 화면이 90분 이상 켜져 있다

전반 45분 + 하프타임 + 후반 45분. 폰을 손에 들고 있든 세워두든 **두 시간 가까이 화면이 꺼지지 않는다.**

→ 여기서는 프레임레이트보다 **배터리와 발열이 지배적인 제약**이다. 60fps로 예쁘게 도는 것보다 안 돌 때 완전히 멈추는 게 훨씬 중요하다.

### ③ 기기 자원을 이미 영상이 쓰고 있다

| 시나리오 | 상황 |
|---|---|
| **TV로 경기 + 폰으로 채팅** | 폰은 우리 것만 돌리지만 2시간 내내 화면 ON |
| **폰 하나로 분할/PiP** | 1080p 하드웨어 디코딩이 이미 GPU를 쓰는 중. 90분이면 이미 뜨겁다 |
| **PC에서 중계 창 + 채팅 탭** | 채팅 탭이 비활성일 때가 많음 → 브라우저가 rAF를 자동으로 멈춤 |

→ 우리가 GPU를 쓰는 건 **영상 디코딩과 경쟁하는 것**이다. 여유가 있다고 가정하면 안 된다.

### ④ 중계는 실시간보다 늦다

쿠팡플레이 같은 OTT 중계는 실제 경기보다 수십 초~1분 이상 늦는 경우가 있다.

→ 나중에 서버 골 이벤트를 붙이면 **중계에서 골이 나오기 전에 우리 화면이 먼저 터질 수 있다.** 지금은 테스트 버튼으로만 켜지지만, 실제 연결 시엔 반드시 고려해야 한다. (10절에 남김)

### 정리하면

| 우선순위 | 항목 |
|---|---|
| 1 | 배터리·발열 (90분 상시 + 영상과 경쟁) |
| 2 | 진입 속도 (경기 직전 동시 접속이 몰린다) |
| 3 | 채팅 가독성 (연출이 글을 가리면 안 됨) |
| 4 | 시각적 화려함 |

**4번이 마지막이라는 게 이번 판단의 핵심이다.** 그래서 "신기술을 써본다"가 목표였던 처음 생각을 접었다.

## 2. 그래서 정한 기준

기술을 고를 때 매번 이 순서로 물었다.

1. **CSS로 되나?** → 되면 CSS. 이미 GPU 합성으로 처리되고 추가 비용이 없다.
2. **안 되면 Canvas 2D로 되나?** → 되면 Canvas 2D. 폴백이 필요 없고 코드가 짧다.
3. **그것도 안 되면 WebGL.** → 왜 안 되는지 숫자로 설명할 수 있어야 한다.
4. **WebGPU는 WebGL로도 안 될 때만.**

한 계단 올라갈 때마다 **코드량, 폴백 경로, 초기화 비용**이 늘어난다. 그래서 "더 멋져서"가 아니라 "아래 단계로는 계산이 안 나와서" 올라가야 한다고 봤다.

## 3. 무엇을 어디에 썼나

| 연출 | 기술 | 왜 이 단계인가 |
|---|---|---|
| 골 조명 쇼 | **WebGL2** | 픽셀 단위 계산이라 아래 단계로는 초당 연산량이 안 나옴 |
| LED 곡면 보드 | **WebGL2** + Canvas 2D 텍스처 | CSS `transform`으로는 **표현식 자체가 없음** |
| 승리 색종이 | **Canvas 2D** | WebGL이 이기는 구간에 도달하지 못함 |
| 흔들림·섬광·배경 | **CSS** | 이미 GPU 합성. 옮길 이유 없음 |
| WebGPU | **미채택** | 강점이 작용할 지점이 워크로드에 없음 |

## 4. 각각 왜 그 선택이 합리적인가

**측정 기준** 방 최대 폭 896px, 경기장 영역 896×420, 보드 896×52, 프레임 예산 16.7ms(60fps).

### 4.1 골 조명 → WebGL

조명 5개가 각도에 따라 빔을 쏘는 연출이다. 계산해봤다.

```
프래그먼트 수    896 × 420 × DPR 1.5²  =  846,720
프래그먼트당     광원 5개 × (atan2 + exp + pow + length + sin) ≈ 170 연산
프레임당                                ≈  1.44억 연산
초당 (60fps)                            ≈  86억 연산
```

| 실행 위치 | 처리량 | 판정 |
|---|---|---|
| JS 단일 스레드 (Canvas 2D 픽셀 루프) | 초당 0.5~2억 | **40~170배 부족** |
| GPU | 초당 5천억 이상 | 약 1.7% 사용 |

Canvas 2D로 하려면 `ImageData`를 받아 84만 픽셀을 JS `for`문으로 도는 구조가 된다. **수학 연산을 다 빼고 루프만 돌려도** 프레임 예산을 넘긴다. CSS는 픽셀별 계산이라는 개념 자체가 없다.

**이건 "WebGL이 더 빠르다"가 아니라 "아래 단계로는 만들 수 없다"에 해당한다.** 그래서 올라간 게 합리적이라고 봤다.

**사용 환경 반영** — DPR 상한을 2가 아니라 **1.5**로 잡았다. 프래그먼트 수는 DPR의 제곱에 비례해서, `2.0² → 1.5²`면 **44%가 줄어든다.** 부드러운 그라디언트라 화질 차이는 눈에 안 띈다. 영상 디코딩과 GPU를 나눠 쓰는 상황이라 이 정도는 깎는 게 맞다고 판단했다.

### 4.2 LED 곡면 보드 → WebGL

여기는 속도 문제가 아니었다.

처음엔 CSS로 만들었다. `mask-image`로 실루엣을 휘게 깎고 `perspective + rotateX`로 기울였다. 꽤 그럴싸했는데 **한 가지가 끝내 안 됐다.**

진짜 360도 링이라면 맞은편(화면 가운데) 글자가 좁아 보여야 한다. 그런데 CSS `transform`은 **평면 하나에 대한 변환 행렬**이라, 열마다 다른 배율을 적용할 수가 없다. 원근 압축은 열마다 `1/z` 나눗셈이 필요한데 그 표현식이 없다.

**CSS로 억지로 흉내낸다면:**

```
기둥 96개 × 보드 내용 12판 ≈ DOM 노드 1,150개
각각 개별 transform + overflow 클립
골 스크롤 중 매 프레임 갱신
```

**실제 구현:**

```
정점 194개 → 정점 셰이더 194회
프래그먼트 1792 × 104 = 186,368 → 텍스처 페치 1회 + 약 15 연산
프레임당 CPU 작업 → uniform 1개 쓰기 + 드로우콜 1회
```

노드 1,150개 대 드로우콜 1회. **이건 비교가 안 된다고 봤다.**

**왜 텍스처 방식이 합리적인가** — 보드 글자를 GPU에 직접 넣을 방법이 없어서 canvas 2D로 한 번 굽고 텍스처로 올린다. 처음엔 "매 프레임 다시 구워야 하나?" 싶었는데, 생각해보니 **보드 내용은 점수·시계·득점자가 바뀔 때만 달라진다.** 스크롤은 UV 좌표만 밀면 된다.

| | 매 프레임 굽기 | 내용 변경 시만 (채택) |
|---|---|---|
| 텍스트 래스터 | 1~3ms/프레임 | 0 |
| 텍스처 업로드 | 745KB × 60 = **44.7MB/s** | 745KB/s |
| 프레임당 작업 | 전부 | **uniform 1개** |

**60배 차이다.** 90분 켜두는 화면에서 이 차이는 배터리로 그대로 돌아온다.

### 4.3 승리 색종이 → Canvas 2D (WebGL 안 씀)

조명을 WebGL로 막 만든 직후라 관성적으로 또 WebGL을 쓸 뻔했다. 다시 계산해보니 **구조가 정반대**였다.

```
물리 갱신     520개 × 25 연산        =  13,000 연산/프레임   ← 무시 가능
래스터라이즈  520개 × 108px × DPR 2² = 224,640 px/프레임     ← 0.3~1ms
API 호출      520개 × 3~4회          ≈ 1,500~2,000회/프레임 ← 0.4~2ms  ★ 지배적
```

지배 비용이 **픽셀이 아니라 Canvas 2D API 호출 횟수**다. 그리고 이게 정확히 WebGL이 해결하는 지점이다(인스턴싱으로 드로우콜 1회).

그런데 절감액을 따져보니:

| | Canvas 2D | WebGL |
|---|---|---|
| 프레임당 | 1~3ms (예산의 6~18%) | 0.3~0.5ms |
| 절감액 | — | 약 **1.5ms** |
| 고정 비용 | 0 | 셰이더 컴파일 1~5ms(1회) + GL 컨텍스트 하나 더 + 폴백 경로 |

**교차점을 계산해봤다.** API 호출 비용은 조각 수에 선형이니, 520개에 2ms면 **4,000~5,000개에서 프레임 예산을 다 먹는다.** 거기가 WebGL이 이기기 시작하는 지점이다.

그런데 색종이 5,000개면 화면이 흰색·빨간색으로 덮여서 아무것도 안 보인다. **도달할 수 없는 교차점을 위해 고정 비용을 내는 셈**이라 안 쓰기로 했다.

여기에 사용 환경이 더 얹혔다. GL 컨텍스트를 하나 더 만든다는 건 **영상 디코딩과 GPU 메모리를 더 나눠 쓴다**는 뜻이다. 1.5ms 아끼자고 할 일은 아니었다.

### 4.4 흔들림·섬광·배경 → CSS

`transform`과 `opacity`만 쓴다. 이 둘은 합성 단계에서만 처리돼서 **레이아웃 0, 페인트 0**이다. 이미 GPU가 하고 있으니 WebGL로 옮겨도 얻을 게 없다.

**여기서 실제로 실수한 게 있다.** 화면 전체를 덮는 섬광을 `background-position`으로 움직이고 있었는데, 이 속성은 합성으로 처리되지 않아서 **매 프레임 레이어 전체를 다시 칠한다.**

```
896 × 420 × DPR 2² = 1,505,280 px 재페인트 / 프레임 → 초당 9천만 px
```

하필 조명 쇼가 GPU를 쓰는 그 5초에 겹쳐 있었다. `transform`으로 바꾸니 재페인트가 0이 됐다.

**교훈** — "CSS 애니메이션이니까 가볍겠지"가 아니라 **어떤 속성을 애니메이션하느냐**가 전부였다.

## 5. WebGPU 이야기

솔직히 제일 쓰고 싶었던 기술이다. 그래서 억지로라도 쓸 곳이 있는지 찾아봤고, 결론은 **없다**였다.

WebGPU의 강점 세 가지를 우리 워크로드에 대입했다.

**① 드로우콜 제출 오버헤드 감소**

```
현재 드로우콜        렌더러당 프레임 1회 (총 2개)
WebGL 드로우콜 비용  약 1~10μs
프레임 예산          16,667μs
차지 비율            최대 0.06%
```

WebGPU가 이걸 5~10배 줄여준다 쳐도 **0.06%의 90% = 0.054% 절감**이다. 측정도 안 되는 수준이다. 이 강점은 드로우콜이 수천 개일 때 의미가 있는데 우리는 2개다.

**② 컴퓨트 셰이더**

화면에 안 그리는 GPU 범용 연산이 하나도 없다. 물리 시뮬레이션도, ML 추론도 없다. WebGPU의 가장 큰 추가점인데 쓸 데가 없었다.

**③ 워커 스레드 커맨드 기록**

커맨드 기록량이 프레임당 드로우콜 1회다. 병목이 아닌 걸 병렬화해도 얻는 게 없다.

**반대로 비용은 확실하다:**

| 항목 | 비용 |
|---|---|
| `requestAdapter` + `requestDevice` | 비동기, 첫 호출 5~50ms — **방 입장 크리티컬 패스에 얹힘** |
| 렌더 경로 이중화 | WGSL + WebGL 폴백 = 셰이더 2벌 유지 |

경기 직전엔 사용자가 한꺼번에 들어온다. **입장이 느려지는 건 우리 서비스에서 제일 아픈 지점**이라, 측정도 안 되는 이득을 위해 여기에 밀리초를 얹을 수는 없었다.

> **언제였으면 썼을까** — 관중 5만 명을 개별 렌더링하거나, 파티클끼리 충돌시키거나, 브라우저에서 ML 추론을 돌렸다면. 셋 다 컴퓨트 셰이더나 수만 단위 인스턴싱이 필요해서 WebGL로는 구조적으로 안 된다. **WebGPU를 안 쓴 게 아니라 쓸 문제가 없었다**는 게 더 정확한 표현 같다.

## 6. Vercel 배포 관점

프론트를 Vercel에 올리고 있어서, 이것도 판단에 들어갔다.

**① 연출은 전부 클라이언트 사이드다**

셰이더도 캔버스도 사용자 브라우저에서 돈다. **서버리스 함수 호출이 0**이라 Vercel 비용에 영향이 없다. 아무리 화려하게 만들어도 청구서가 늘지 않는다는 뜻이라, 여기서는 제약이 아니었다.

**② 대신 번들 크기가 직접 영향을 준다**

Vercel은 정적 자산을 CDN 엣지에서 준다. 빠르긴 한데 **파일이 작을수록 빠른 건 여전히 같다.**

경기 직전에 접속이 몰리고, 상당수가 모바일 데이터다. 여기서 Three.js gzip 100KB를 얹으면 **첫 진입이 그만큼 늦어진다.** 정작 그걸 쓰는 건 골이 터진 5초뿐인데.

| 후보 | 판정 |
|---|---|
| Three.js (`WebGLRenderer`) | ❌ 필요한 건 드로우콜 1회 + 셰이더 2장뿐 |
| 파티클 라이브러리 | ❌ 120줄로 직접 쓰는 게 짧고 통제됨 |

**결과적으로 그래픽 관련 의존성 추가는 0이다.** 이게 이번 작업에서 제일 마음에 드는 부분이다.

**③ 폰트도 이미 있는 걸 썼다**

보드 서체로 `Bebas Neue`를 골랐는데, **프로젝트가 이미 `next/font`로 싣고 있던 폰트**였다. next/font는 Google Fonts를 빌드 때 받아서 자체 호스팅하므로 외부 요청도 없고 Vercel CDN에서 같이 온다. 추가 비용 0.

**④ 앞으로 볼 것**

경기장 사진(`public/metropolitano-day.jpg`)이 `/public`에서 나간다. 경기 직전 동시 접속이 몰리는 서비스라 **CDN 대역폭은 나중에 확인이 필요하다.** WebP/AVIF 변환이나 `next/image` 적용을 검토해볼 만하다.

## 7. 성능 원칙 — "평상시 비용 0"

1절의 제약(90분 + 영상과 경쟁)에서 곧바로 나온 원칙이다.

```
90분 상시 rAF          = 324,000 프레임
프레임당 0.3ms만 써도  = 누적 97초의 연속 GPU 가동
```

이미 영상 디코딩으로 뜨거운 기기에 이걸 얹으면 발열 스로틀링으로 **중계 영상이 끊길 수도 있다.** 우리 연출 때문에 사용자가 경기를 못 보는 건 최악이다.

그래서 모든 렌더러가 같은 규칙을 따른다.

> **컨텍스트는 입장할 때 한 번 만들고, rAF는 연출 중에만 돌고, 끝나면 스스로 멈춘다.**

| 렌더러 | 실제 가동 | 90분 대비 |
|---|---|---|
| 조명 | 골당 5초 | 골 3개 기준 **0.3%** |
| 색종이 | 승리 9초 + 잔여 낙하 | **0.2%** |
| 보드 | 평상시 초당 1드로우(시계) + 골 5초 | **1.7%** |

컨텍스트를 미리 만들어두는 이유는 따로 있다. 골 순간에 셰이더를 컴파일하면 **1~5ms가 하필 그 프레임에 얹혀서** 연출 첫 순간이 튄다.

덤으로, PC에서 채팅 탭을 뒤로 보내두면 브라우저가 알아서 rAF를 멈춘다. 우리가 상시 루프를 돌리지 않으니 **탭 복귀 시에도 밀린 프레임을 몰아 처리하는 일이 없다.**

## 8. 삽질 기록

가장 오래 붙잡은 것들. 이쪽이 실제로 배운 부분이다.

| 증상 | 원인 |
|---|---|
| 개발 모드에서 셰이더 컴파일 실패 (에러 로그가 `null`) | 정리 함수에서 부른 `loseContext()`가 컨텍스트가 아니라 **캔버스를** 죽인다. React StrictMode가 마운트를 두 번 돌려서 두 번째가 죽은 컨텍스트를 받았다 |
| 컨텍스트 복구 후 화면이 비어 있음 | 복구 시 GL 상태가 초기화되는데 캔버스 크기는 그대로 → "크기 바뀔 때만" 뷰포트를 걸던 코드가 건너뜀 |
| 연출 끝에 화면 중앙에 커다란 띠가 남음 | 섬광 애니메이션 2.3초 < 연출 5초. `animation-fill-mode` 기본값이 `none`이라 끝나면 원위치(화면 중앙)로 복귀. **처음엔 WebGL을 의심했는데 CSS였다** |
| WebGL 보드가 폴백 글꼴로 렌더 | `ctx.font` 지정만으로는 웹폰트를 안 내려받는다. 게다가 텍스처는 정적이라 폰트가 늦게 와도 갱신이 안 된다 → `document.fonts.load()` 후 **다시 굽기** |
| 곡면이 평평하게 나옴 | 카메라 눈높이를 보드 바깥에 두어 위아래가 같은 방향으로 휘었다. 눈높이를 보드 상·하변 사이로 옮기니 해결 |
| 밝은 배경에서 흰 요소가 사라짐 | 조명은 배경을 눌러 해결(5초라 가능). 색종이는 9초라 배경을 못 눌러서 **조각 뒷면을 어둡게 + 앞면 테두리**로 해결. 같은 문제인데 지속 시간 때문에 해법이 갈렸다 |
| 모듈 해석 충돌 | `winConfetti.ts` / `WinConfetti.tsx`가 대소문자만 달랐다. 대소문자 비구분 파일시스템에서 충돌 → 로직 파일에 기술 접미사(`...GL.ts`, `...Canvas.ts`) 규칙 도입 |

## 9. 안전장치

연출이 화려할수록 빠져나갈 구멍이 필요하다고 생각했다.

| 상황 | 처리 |
|---|---|
| `prefers-reduced-motion` | 컨텍스트를 아예 안 만든다. CSS 연출도 `display: none` |
| WebGL 사용 불가 | 조명·색종이는 조용히 생략, **보드만 CSS 폴백으로 전환** |
| 컨텍스트 손실 | `webglcontextlost` 차단 후 `restored`에서 재구성 |
| 광과민성 | 깜빡임 최저값을 0이 아닌 0.62로 제한 |
| 스크린리더 | 연출 층 전부 `aria-hidden` |
| 가독성 우선 | "배경 흐리게" 토글 시 조명 세기 절반 |

`prefers-reduced-motion`에서 `animation: none`이 아니라 `display: none`을 쓴 이유도 적어둔다. **애니메이션만 멈추면 섬광 띠가 화면 한복판에 선 채로 5초를 버틴다.**

보드만 폴백을 따로 둔 이유는, 조명이나 색종이는 없어도 나머지가 남지만 **보드는 빠지면 헤더 아래가 빈 자리로 드러나기** 때문이다.

## 10. 요약

> 경기 채팅방 사용자가 **쿠팡플레이로 경기를 보면서 90분 이상 켜두는** 환경이라는 걸 먼저 정리하고, 배터리·발열과 진입 속도를 시각적 화려함보다 위에 뒀다. 그 기준으로 CSS → Canvas 2D → WebGL 순으로 올라가며, **아래 단계로 계산이 안 나오는 것만** 위로 올렸다. 픽셀 단위 계산(조명, 초당 86억 연산)과 평면 변환으로 표현이 불가능한 곡면(LED 보드)에만 WebGL2를 썼고, 물체 단위 워크로드(색종이)는 WebGL 교차점이 도달 불가능한 규모라 Canvas 2D로 남겼다. WebGPU는 최대 강점인 드로우콜 배칭이 프레임 예산의 0.06%에만 작용하고 컴퓨트 셰이더 수요가 없어, 초기화 5~50ms만 크리티컬 패스에 얹히는 구조라 미채택했다. Vercel 배포라 연출의 서버 비용은 0이지만 번들 크기는 진입 속도에 직결돼 **그래픽 라이브러리는 추가하지 않았고**, 모든 렌더 루프를 연출 중에만 가동시켜 상시 점유를 **1.7% 이하**로 유지했다.

## 11. 남은 일

- **실기기 프로파일링** — 이 문서의 수치는 산술 추정이다. 특히 **폰 하나로 쿠팡플레이 + 채팅 분할** 상황에서 골 연출이 영상 재생에 영향을 주는지 반드시 재봐야 한다. Chrome DevTools Performance로 프레임 타임과 GPU 점유를 측정할 것.
- **중계 지연과 골 연출 타이밍** — 서버 골 이벤트를 붙이면 **중계보다 우리 화면이 먼저 터질 수 있다.** 스포일러가 된다. 지연 보정 옵션이나 "결과 미리 보지 않기" 설정이 필요할지 검토.
- **골·경기 종료 이벤트 채널** — 지금은 개발용 테스트 바로 연출을 켠다. 서버 이벤트 연결 후 테스트 바 제거.
- **경기장 사진 최적화** — `public/metropolitano-day.jpg`가 CDN에서 나간다. 동시 접속이 몰리는 서비스라 WebP/AVIF나 `next/image` 검토.
- **보드 라틴 표기 매핑** — `boardNames.ts`의 대회·팀명 표는 스쿼드·일정이 바뀌면 낡는다. 서버가 라틴 표기를 함께 내려주는 게 맞다.
- **리그 배지** — 라리가·챔스 로고는 상표와 저작권 이중 보호라 못 쓴다(데이터 API를 거쳐도 같다. API 제공자가 상표권자가 아니므로 없는 권리를 넘겨줄 수 없음). 대회별 색 + 약칭으로 자체 SVG 제작 검토.
